# Day 89: Where Ground Truth Comes From — Calibrating the Harness Against Real Rollouts

## TL;DR
Day 88 built a simulation harness with known ground truth, used it to catch adaptive clustering inflating the canary's false-positive rate from a nominal 5% to 11.2%, and then turned the harness into a standing preflight check. It ended on the obvious weakness: every scenario the harness generates was written by the same person who wrote the mechanism being tested. If the author's mental model of "what correlation drift looks like" is wrong, the harness will faithfully test the wrong thing and report a clean bill of health. Today goes looking for independent ground truth, and the only candidate is the one source nobody authored: the canary rollouts that have actually happened since Day 84. There are 14 of them, which is a tiny sample, skewed toward the failures that somebody noticed, with labels that arrive weeks late and are sometimes wrong. Today builds the machinery to use that corpus anyway: a rollout outcome store with honest label provenance, replay of real recorded streams through the monitors, a measured fidelity score for the harness, and scenario reweighting that shrinks toward the real data in proportion to how much of it there is.

## The Problem
- The validity check from Day 88 compares a mechanism's realized error rates to its claimed ones, and "realized" is computed on scenarios generated by `generate_stream`. That function encodes assumptions: correlation changes happen as step changes or linear ramps, request volumes are steady, signal failures are Bernoulli draws coupled through one latent variable. Each assumption is plausible and none was checked against anything real. A mechanism can pass the check because it handles the harness's idea of drift, while real drift looks different.
- This is the same structural problem Day 78 found in the burst-test harness and Day 82 found in the taxonomy: a verification instrument whose validity rests on its author's imagination. Those days could only name the ceiling. This is the first case in the arc where an outside reference exists, because canary rollouts since Day 84 have produced real streams with real outcomes.
- The reference is weak in four specific ways, and a design that ignores them will be worse than having no reference at all. First, it's small: 14 labeled rollouts. Second, it's biased toward noticed events: a rollout that degraded quietly and was promoted looks identical to a healthy one until something surfaces later, so "promoted and nothing happened" is weak evidence of health. Third, labels are delayed: a rollout promoted three days ago can't be labeled healthy yet because the failures that would disqualify it haven't had time to appear. Fourth, the corpus is range-restricted: every mechanism in it already cleared the preflight gate, so the corpus says nothing about what gate-failing mechanisms look like in production, which is exactly the population the gate is supposed to keep out.
- Two things make using the corpus feasible at all. Day 87's ledger design means every canary stage's raw observations were recorded, so any real rollout can be replayed through any monitor version, including ones that didn't exist when it ran. And Day 49's replay machinery already exists for comparing behavior across runs of the same operation. The data is there. What's missing is a way to treat it as evidence rather than anecdote.

## Architecture

### 1. A rollout outcome store with explicit label provenance
Every completed canary gets a record, and the record's label is not a boolean. It carries where the label came from, how confident it is, and how old it is, because a label confirmed by an incident review is worth far more than one inferred from silence.

```python
class LabelSource(Enum):
    ROLLBACK_CONFIRMED_BAD = "rollback_confirmed_bad"      # rolled back, post-incident review agreed
    ROLLBACK_JUDGED_FALSE_ALARM = "rollback_false_alarm"   # rolled back, review found no real problem
    PROMOTED_HELD = "promoted_held"                        # promoted, survived the hold window quiet
    PROMOTED_LATE_BAD = "promoted_late_bad"                # promoted, a defect surfaced later
    UNLABELED_PENDING = "unlabeled_pending"                # too recent to say anything

@dataclass
class RolloutRecord:
    rollout_id: str
    mechanism: str
    ledger_snapshot_ref: str           # Day 87 observation ledger, stored by reference
    monitor_verdict: str               # what the live monitor decided
    label: LabelSource
    label_confidence: float            # 0.95 for incident-reviewed, 0.60 for "held quietly"
    labeled_at: float | None
    hold_window_days: int = 14

def effective_truth(rec: RolloutRecord) -> bool | None:
    """True = mechanism was truly degraded. None = no usable label."""
    if rec.label in (LabelSource.ROLLBACK_CONFIRMED_BAD, LabelSource.PROMOTED_LATE_BAD):
        return True
    if rec.label in (LabelSource.ROLLBACK_JUDGED_FALSE_ALARM, LabelSource.PROMOTED_HELD):
        return False
    return None    # pending labels are excluded, never assumed healthy
```

The last line is the one that matters most. A rollout inside its hold window is excluded from every calibration statistic. Counting it as healthy because nothing has gone wrong yet is the survivorship error: it converts "we haven't looked long enough" into "it's fine."

### 2. Replaying real streams through current monitors
Because each record points at a full ledger snapshot, calibration can run the real observation stream through today's monitor, Day 85's, Day 86's, or Day 88's, and compare verdicts to the label. This turns the small corpus into a direct test of the thing that matters: does the monitor reach the right verdict on streams nobody authored.

```python
def replay_agreement(monitor_factory, corpus: list[RolloutRecord]) -> dict:
    tp = fp = tn = fn = 0
    disagreements = []
    for rec in corpus:
        truth = effective_truth(rec)
        if truth is None:
            continue
        ledger = ledger_store.load(rec.ledger_snapshot_ref)
        monitor = monitor_factory()
        verdict = None
        for obs in ledger.iter_in_order():
            monitor.ingest(obs)
            verdict = monitor.stage_verdict()
            if verdict in ("REGRESSED", "HEALTHY"):
                break
        predicted_bad = (verdict == "REGRESSED")
        tp += predicted_bad and truth
        fp += predicted_bad and not truth
        tn += (not predicted_bad) and (not truth)
        fn += (not predicted_bad) and truth
        if predicted_bad != truth:
            disagreements.append((rec.rollout_id, rec.label, verdict))
    return {"tp": tp, "fp": fp, "tn": tn, "fn": fn, "disagreements": disagreements}
```

Run against the 14 labeled rollouts (9 promoted-and-held, 3 rollback-confirmed-bad, 1 rollback judged a false alarm, 1 promoted-and-later-found-bad):

day85_independent              3   2   7   2     10/14
day86_fixed_clusters           3   1   8   2     11/14
day88_budgeted_adaptive        3   1   8   1     12/14

The ordering of the three monitors matches what the harness predicted: each design is at least as good as the one before. That's the first independent confirmation that the harness ranks designs sensibly. The two disagreements are worth reading by hand. One is a false alarm (a real false positive, consistent with the measured 5% alpha). The other is a mechanism that was promoted and later turned out bad: a false negative that only exists in the corpus because someone eventually noticed it. Without the late-label path in step 1 it would be recorded as a healthy rollout and the monitor would look perfect.

### 3. Measuring harness fidelity with a feature-distribution comparison
Agreement on 14 streams says the monitors are plausible. It doesn't say whether the 4,000 synthetic scenarios resemble reality, which is what the validity check actually depends on. Fidelity is measured by extracting the same summary features from real and synthetic streams and comparing their distributions.

```python
FIDELITY_FEATURES = {
    "base_error_rate":          lambda s: s.marginal_error_rate(),
    "median_pairwise_corr":     lambda s: s.median_abs_correlation(),
    "corr_change_events":       lambda s: s.count_correlation_epochs() - 1,
    "events_per_stage":         lambda s: s.n_events,
    "burstiness":               lambda s: s.fano_factor_of_failures(window=60),
}

def harness_fidelity(real_streams, synthetic_streams) -> dict:
    per_feature = {}
    for name, fn in FIDELITY_FEATURES.items():
        real = np.array([fn(s) for s in real_streams])
        syn = np.array([fn(s) for s in synthetic_streams])
        ks = scipy.stats.ks_2samp(real, syn).statistic     # 0 = identical, 1 = disjoint
        per_feature[name] = 1.0 - ks
    # a single scalar is convenient but hides which feature is wrong, so keep both
    return {"per_feature": per_feature, "overall": float(np.mean(list(per_feature.values())))}
```

```
feature                 fidelity   note
base_error_rate           0.86     close
median_pairwise_corr      0.58     real median 0.31 vs synthetic 0.52 -- harness runs hot
corr_change_events        0.49     50% of synthetic stages drift vs 3 of 14 real (21%)
events_per_stage          0.71     real stages are lower-volume than synthetic
burstiness                0.55     real failures cluster more than Bernoulli draws allow
overall                   0.64
```

The fidelity score is a number to look at last. The per-feature breakdown is where the action is. The harness over-represents correlation drift by more than 2x and over-states correlation magnitude, which means Day 88's measured false-positive rate for adaptive clustering (11.2%) was probably worse than reality would produce, because the harness gave the adaptive machinery more drift to misfire on. And it under-represents burstiness, which cuts the other way: real failures arrive in clumps, which an SPRT handles differently from independent draws. The two errors don't cancel. They're different biases with different directions, and a single overall score would have hidden that.

### 4. Reweighting scenarios toward the real corpus, shrunk by sample size
The harness's scenario mix gets adjusted toward the observed feature distribution, but only as far as 14 samples justify. The blend weight is the standard shrinkage form: the real corpus's influence is `n / (n + k)`, where `k` is a prior strength that says how many real samples it takes to outvote the author's assumptions.

```python
def reweight_scenarios(scenarios: list[SyntheticRun], real_features: dict,
                       n_real: int, prior_strength_k: int = 30) -> list[tuple[SyntheticRun, float]]:
    w_real = n_real / (n_real + prior_strength_k)         # 14/(14+30) = 0.32
    weighted = []
    for run in scenarios:
        f_syn = scenario_features(run)
        # density ratio: how much more (or less) common is this scenario shape in the real corpus
        ratio = kde_density(real_features, f_syn) / max(kde_density(synthetic_features, f_syn), 1e-9)
        weight = (1 - w_real) * 1.0 + w_real * ratio       # blend uniform with importance weight
        weighted.append((run, float(np.clip(weight, 0.1, 5.0))))   # clipped: no scenario vanishes or dominates
    return weighted
```

At `n=14` and `k=30`, real data carries 32% of the weight. When the corpus grows to 60 labeled rollouts that becomes 67%. The clipping bounds matter: without them a single unusual real stream could make the importance weights spike and let one outcome dominate a thousand scenarios, or let regions the real corpus happens not to cover be weighted to zero, which would quietly delete exactly the adversarial cases Day 81 taught the arc to keep.

### 5. The harness gets its own trust score, in shadow mode
The same pattern Day 59 applied to the AST analyzer and Day 78 applied to the test harness now applies to the validity harness: run it in shadow mode, track how often its predictions match what happens in the real corpus, and let its authority grow with its record. Concretely, for each real rollout the harness predicts what the monitor's verdict should be on a synthetic twin of that stream, and the trust score tracks the agreement rate.

```python
class HarnessTrust:
    def __init__(self):
        self.agree = 0
        self.total = 0

    def record(self, harness_prediction: str, real_verdict: str):
        self.total += 1
        self.agree += (harness_prediction == real_verdict)

    def score(self) -> tuple[float, float, float]:
        # Wilson interval: honest about how little n=14 can say
        n, p = self.total, self.agree / max(self.total, 1)
        z = 1.96
        denom = 1 + z * z / n
        center = (p + z * z / (2 * n)) / denom
        half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
        return p, center - half, center + half
```

```
harness trust: agreement 11/14 = 0.79, 95% interval [0.52, 0.92]
harness fidelity (overall, from step 3): 0.64
```

The interval is the finding. 0.79 agreement sounds good, but with 14 samples the true value could plausibly be as low as 0.52. The calibration process has produced a trust estimate whose uncertainty is large enough that the next question isn't "is the harness good" but "what should the gate do with a harness whose trustworthiness is this uncertain."

## Failure Modes
- **The corpus is range-restricted by the gate it's meant to validate.** Every rollout in it cleared Days 79 through 88's checks before shipping, so it contains no examples of the mechanisms the gate exists to reject. The calibration can say whether the harness resembles passing mechanisms in production. It cannot say whether the harness catches the failures that would have come from mechanisms the gate blocked, because those never produced production streams. This is a structural blind spot, not a sample-size problem, and more rollouts won't fix it.
- **Label noise has no ground-truth reference of its own.** A `PROMOTED_HELD` label means no defect surfaced within 14 days, with confidence 0.60. Slow failures (a resource leak that takes a month, a staleness bug that needs a rare upstream state) would be labeled healthy. The corpus's "healthy" class is contaminated by an unknown fraction of undetected bad rollouts, which makes every false-positive estimate computed against it optimistic.
- **Reweighting toward 14 streams can fit noise.** With one real rollout accounting for roughly 2% of the real corpus's weight, and kernel density estimation on five features, the importance ratios are noisy. The clipping bounds and the shrinkage factor limit the damage, but `prior_strength_k=30` is a judgment call, not a derived constant. It determines how fast the harness follows the data and is only defensible as a conservative guess.
- **The system is non-stationary and the corpus ages.** Rollouts from Day 84 ran under traffic mixes, upstream behaviors and mechanism sets that have since changed. Treating a 6-week-old stream as equally representative of today's production as last week's stream assumes the world is stable, which Day 67's regime-segmented baselines exist precisely because it isn't.

## What's Next
Calibration produced a fidelity score of 0.64 and a harness trust estimate of 0.79 with an interval of [0.52, 0.92]. Those are honest numbers, and they're awkward to act on. A preflight check that depends on a harness this uncertain cannot be a clean pass/fail without either overstating its confidence or blocking mechanisms on weak grounds. Day 90 asks what a gate verdict should look like when the check's own reliability is a range rather than a point, and whether "pass or block" is even the right set of outcomes.
